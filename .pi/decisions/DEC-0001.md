# DEC-0001 — the payload transport decides the demuxer, and MPEG-PS is not disturbed

## Statement

Every session reads its leading video packets before starting FFmpeg, classifies the transport
from that prefix, and then:

- **MPEG-PS** → the `mpeg` demuxer, and the bodies are written unchanged. Same argv, same bytes
  as before the RTP path existed.
- **RTP** → each packet goes through `RtpDepacketizer` (RFC 6184 H.264 and RFC 7798 HEVC: single
  NAL units, STAP-A/AP aggregates, FU-A/FU fragments) and FFmpeg is started with `-f h264` or
  `-f hevc` plus `-use_wallclock_as_timestamps 1`.
- **Unrecognised, or RTP with no parameter set to name its codec** → the `mpeg` demuxer it has
  always used, plus a warning. A session is never refused because the bridge failed to recognise
  its payload: the transport can be read wrong in one direction, and refusing to serve a stream
  that would have worked is worse than serving one that produces nothing.

## Reason

The RTP header alone is not enough to decide, and neither is a single packet's first byte: a
VTM packet may begin mid-pack, and a mid-stream byte that reads as RTP is what 0.1.5's
per-packet check kept reporting as a fault. Hence a buffered prefix, up to eight packets with a
non-empty body.

The cost is accepted deliberately: up to eight packets of added latency on every session,
including MPEG-PS ones, because the demuxer has to be chosen before FFmpeg starts.

## Context / relations

`tools/verify_rtp_against_addon.sh` is the gate for this invariant: it builds a synthetic H.264
and HEVC elementary stream, packetizes it as RFC 6184 and RFC 7798 prescribe, pushes it through
the real depacketizer, and feeds the result to the FFmpeg the add-on image actually installs,
using the argv `_start_ffmpeg` produces. A change to the depacketizer or to that argv must be
re-verified there, not only on the development machine's ffmpeg.

Not covered, deliberately: H.264 FU-B and HEVC PACI (dropped and counted), layered HEVC streams
with `nuh_layer_id >= 32`, and a second payload type carrying media on the same VTM channel (the
depacketizer filters on the payload type the codec was identified from).

## Evidence

`session.py` holds `_MPEG_PS_DEMUXER`, `_decide`, `_read_prefix` and `_start_ffmpeg`; `rtp.py`
holds `detect_codec` and `RtpDepacketizer`.
