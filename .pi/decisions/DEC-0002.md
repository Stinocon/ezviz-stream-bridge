# DEC-0002 — the audio input is decided before FFmpeg starts, and given up if it stops

## Statement

For an RTP session, the leading packets are scanned for a second payload type whose AU sizes
account for every remaining byte of the payload exactly. When one is found, its Access Units are
framed as ADTS and FFmpeg is started with `-f aac -i pipe:<fd>` beside the video input; when none
is found within `audio_window` seconds, the session is served video only. Once started, the audio
input is closed after `_AUDIO_STALL_SECONDS` of silence from the camera.

## Reason

Three things were established by measurement rather than inference, and each one constrains the
design:

- The AU-header section is self-validating: `2 + bits/8 + Σsizes == len(payload)` exactly. That
  makes the same function both the parser and the detection, and it is why a video payload is not
  mistaken for audio by accident.
- FFmpeg blocks in `avformat_open_input` on an input with no data. A session that starts FFmpeg
  with an audio input it has not seen a frame for produces a process that never writes a byte.
- FFmpeg's demuxer thread for an input with no data blocks in `read`, the muxer waits behind that
  stream, the video pipe fills, and the session stops producing while the camera keeps streaming.
  Closing the write end frees the video again. So `audio_window` is not a nicety: it is the
  condition for the second input existing at all, and giving up a stalled audio input is the
  condition for the video surviving it.

The cost is accepted and stated in the log: a camera that sends no audio pays the window once per
session, and a session whose audio stops loses its sound from then on. An MPEG-PS session carries
its audio inside the container and is not touched by any of this.

## Context / relations

Depends on DEC-0001: the audio path only exists where the transport was classified as RTP and a
video codec was named from a parameter set. The AudioSpecificConfig is the one parameter of the
audio path that is not in the payload, so it is a documented constant (`AAC_LC_16K_MONO`) printed
by `describe_config` on every session that uses it -- a camera that differs has to be visible in
the log rather than audible on the speaker.

Not covered: an Access Unit fragmented across packets (`AAC-hbr` forbids it, and a payload whose
sizes do not add up is counted as unreadable), and any camera whose audio is not
MPEG4-GENERIC/AAC-hbr.

## Evidence

`rtp.py` holds `parse_au_section`, `carries_aac_hbr`, `adts_frame`, `describe_config` and
`AacHbrDepacketizer`; `session.py` holds `_with_audio`, `_prefix_audio`, `_Sinks`,
`_end_stalled_audio` and the two-input argv in `_start_ffmpeg`. `tools/verify_rtp_against_addon.sh`
is the gate: it rebuilds the ADTS from the same Access Units FFmpeg wrote and compares the bytes,
then asserts the muxed MPEG-TS carries an audio stream that decodes.
