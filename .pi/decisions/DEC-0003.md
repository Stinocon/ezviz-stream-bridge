# DEC-0003 — the channel count is read from the payload, the rate is not in it

## Statement

`stream_channels` reads the element id that opens an Access Unit; the session scans the Access
Units of the audio it has already found — through the prefix and, when the audio arrives later,
through the audio window — and takes the first one that names a count. That count replaces the
channel configuration in `AAC_LC_16K_MONO`; the sample rate and the object type are left as the
family's SDP convention has them.

## Reason

This supersedes DEC-0002 on one point only: DEC-0002 says the AudioSpecificConfig "is the one
parameter of the audio path that is not in the payload". That is true of the sample rate and
false of the channel count, and the difference is not academic — the channel count is the half
whose default silences or garbles a stereo camera. The rest of DEC-0002 stands: the payload is
RFC 3640 `AAC-hbr`, the Access Units are reframed as ADTS, the decision to give FFmpeg a second
input is made from the prefix, and a stalled audio input is given up.

Two things had to be careful, and both are measured rather than assumed:

- The first Access Unit is not the one to read. FFmpeg's own AAC encoder opens a stream with a
  fill element that names no channel (16 of its 17 frames name one), so a single reading would
  fall back to the default on a perfectly ordinary stream.
- A cadence is only printed when it could be one. The first version of that line reported
  `722653.5 kHz` for a stream handed over in one burst; the span now has to be a frame duration
  that a legal sampling frequency can produce (10.7-139 ms for 1024 samples at 7.35-96 kHz)
  before the interval is reported at all.

## Context / relations

Supersedes DEC-0002. Depends on DEC-0001 for the transport classification the audio path sits on.

Not covered: the sample rate, which no field in the payload carries (the RTP timestamp counts
samples rather than naming a rate), and a stream whose channel layout is not one element — a
program config element leading the block, or several single channel elements in sequence. The
reading handles the first case by falling back and saying so; the second is not something this
camera family emits.

## Evidence

`rtp.py` holds `stream_channels` and `set_channels`; `session.py` holds `_audio_channels`,
`_audio_config`, `_packet_cadence` and the extended scan in `_with_audio`; the audio leg of
`tools/verify_rtp_against_addon.sh` reports the provenance of the count it used on a stream
FFmpeg's own encoder produced.
