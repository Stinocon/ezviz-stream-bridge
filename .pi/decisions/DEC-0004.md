# DEC-0004 — the audio pipe is never a place to park

## Statement

`_AudioPipe` holds the write end of the descriptor FFmpeg reads the audio from, with
`os.set_blocking(fd, False)`. `write` appends the chunk to a queue and calls `os.write` as long as
the pipe keeps accepting; what is left stays queued and is offered again on every later packet,
video packets included, because those are the packets that keep arriving while FFmpeg is still
busy with the video. Past `_AUDIO_PENDING_BYTES` the oldest chunks are dropped -- whole chunks, so
the ADTS framing stays valid and the loss is a gap rather than a corrupted frame. `dropped` counts
every byte that never reached FFmpeg, the tail still queued at teardown included, and the session
prints it: the counter means "audio that did not get out", not "audio the bound refused".

## Reason

See the frontmatter: the deadlock is reachable in both orders, it is silent, and it survives every
unblocking mechanism this codebase has. The measurement that made the audio-first order necessary
in the first place -- FFmpeg blocks before writing a byte on an input with no frame -- is also
what makes a blocking write on that pipe unsafe.

Two details are deliberate. The queue holds *whole* chunks because a chunk is one packet's Access
Units: dropping bytes would leave the decoder resynchronising inside a frame. And the lock is
taken only around non-blocking calls, so it cannot itself park a thread; it exists so the stall
watchdog's `close` cannot land between a write's check and its syscall, where the descriptor
number could already have been recycled.

## Context / relations

Depends on DEC-0002, which established that the audio input's existence is decided before FFmpeg
starts and that a stalled audio input is given up; this is the other half of keeping the video
alive around an input FFmpeg opens but may not read. Not covered: the video pipe, which is written
by blocking calls on purpose -- FFmpeg is draining it through its probe, and a session whose video
stops has nothing to protect.

## Evidence

`session.py` holds `_AudioPipe`, `_AUDIO_PENDING_BYTES` and the flush-on-every-packet call in
`_Sinks.feed`; `tests/test_session.py` holds the reproduction (a ~112 KiB audio prefix against a
stand-in that reads the video pipe first -- it parks without the fix, and the test then asserts
that what FFmpeg took plus what was lost is every byte the depacketizer produced) and the pipe's
own bounds test. `tools/verify_rtp_against_addon.sh` is the end-to-end check that nothing is lost while
FFmpeg is reading: the ADTS extracted from the muxed stream is byte-identical to the ADTS the
source produced.
